# M0.6 — timed controls and resolved performance replay

M0.6 adds timestamped semantic control capture and a deterministic TOML timeline
compiler for the existing 16-beat demo. Both produce recording schema 1 histories
that replay directly through the mock backend or M0.4 SuperCollider render/play.
No runtime dependencies or frozen musical-object architecture changes are needed.

## Script a timed performance

```sh
mkdir -p recordings
python -m dinad perform examples/first_environment/performance.toml recordings/performance.json --project examples/first_environment/project.toml
python -m dinad replay recordings/performance.json
QT_QPA_PLATFORM=offscreen python -m dinad render recordings/performance.json recordings/performance.wav
pw-play --volume=1.0 recordings/performance.wav
```

A timeline requires `schema_version = 1` and zero or more action tables:

```toml
schema_version = 1
[[actions]]
seconds = 1
command = "set composition.anchor 60"
[[actions]]
seconds = 2
command = "set transport.tempo_bpm 90"
```

Times are nonnegative seconds relative to performance origin, in ascending order;
equal timestamps preserve file order. Unknown fields, invalid commands/settings,
missing fields and actions beyond the current dynamic finish time fail with the
filename. The complete timeline validates before output is published. Commands
are the existing `set`, `adjust`, `undo`, `inspect`, `key TOKEN` and `quit` actions.
`generate` is rejected here: the result is the timed performance, not a fresh
composition from final settings. Select keyboard mappings with `--profile`.

## Capture controls from the keyboard

```sh
python -m dinad capture recordings/take.json --project examples/first_environment/project.toml --profile examples/first_environment/controls.toml
```

Enter commands such as `key +`, `set transport.tempo_bpm 90`, `undo` and `inspect`.
Each completed input line is timestamped against a monotonic clock starting at
capture initialization after project/profile loading. The clock starts before
the capture message is printed, so input-reader startup time is part of the take. Capture ends automatically at
16 beats, even while stdin is idle. Tempo changes adjust this finish time. `quit`,
EOF or Ctrl-C stops early and clips outstanding gates. Empty input is a short
possibly silent take. Raw key listeners and GUI input are not introduced.

Capture records timed intent; sound is produced when the saved history is
rendered or played afterward. There is no concurrent audio feedback, audio-clock
synchronization, rolling OSC dispatch or active-voice retuning in this slice.
It must not be described as a completed live audio-control transport. Human
input timestamps and thread scheduling are approximate; scripted timelines are
the deterministic route. No microphone or audio device opens during capture.

Invalid commands report errors, preserve project state, undo history and action
timestamps, and allow later commands. The valid partial take is saved; exit code
1 records that a command was rejected. Startup/file/timeline errors use exit 2.
Piped input is accepted and EOF terminates capture; use `perform` for exact times.
Output must be new and its parent must exist. Publication is atomic and never
replaces an existing take. Save failures leave prior files intact. Capture does
not continuously checkpoint, so an unhandled process kill can lose the take.

## Timing and musical contracts

- Tempo is piecewise constant. Each control timestamp maps to a beat using the
  previous segment's tempo; the new tempo applies from that timestamp forward.
  Musical end is beat 16. At 120 BPM unchanged duration is 8 seconds; switching
  to 60 BPM at second 1 (beat 2) moves the end to second 15.
- Changes apply to new note onsets, including an onset exactly at a control
  timestamp. Multiple simultaneous controls all resolve before those onsets.
  Existing notes retain pitch and seconds-duration from their original onset.
  Tempo changes do not stretch already-started envelopes. Stopping, including
  reaching beat 16, clips any remaining note gates; backend release/effect tails
  still follow the selected backend's policy.
- The same anchor shifts future pad/arpeggio onsets consistently. The drone and
  any already-started pads stay at their original pitches. This deliberate
  sustained-note policy can create tension after an anchor change.
- A seed change selects future fast-clock values from that seed's existing
  indexed 16-beat demo. It does not restart the clock or consume new values on
  inspection/save. Slow-clock and harmonic phases retain their original beat
  indices. This is not a general mutable generator-state snapshot system.
- Equal-time notes preserve the existing part/definition ordering. A performance
  with no changes preserves the original demo events. Accepted controls alone
  change history; rejected commands do not advance the accepted-time watermark.
- The recording's `metadata.timed_controls` schema 1 includes initial settings,
  ordered changes, sequence, old/new values, seconds, beats, stop and clock policy.
  The final project/profile snapshots are retained. Stop/quit is represented by
  `stop_seconds`; inspect/read-only commands do not add changes. Replay consumes
  stored resolved notes and never invokes the generator or control metadata.
  Older M0.2/M0.3 recordings remain readable.

## Validation and limits

Headless tests exercise boundary ordering, tempo integration, seed continuity,
undo, rollback, early termination, automatic idle completion, timeline validation,
no-clobber output and generator-independent replay. Packaging includes the Python
module; the source distribution also includes examples, documentation and
diagnostic scripts so its tests can run outside the original checkout. The actual
SuperCollider smoke render uses the generated timed history, without claiming
that a successful render establishes listening quality.

M0 acceptance advances to timed capture and reproducible resolved performance
replay. Controls during concurrently running audio, calibrated wired device
latency and sustained-load audio stability remain follow-up work. M0.6 is a
small timing/control slice, not a replacement for the future audio-derived clock.

Local build validation (11 November 2026): 174 tests pass on Python 3.14.8 with
actual SuperCollider 3.13.0, both in the source checkout and against an installed
wheel using the extracted source distribution's tests. One hundred seeded
mixed-tempo/anchor timelines retain all 61 onsets and compile for SuperCollider.
The example produces byte-identical resolved histories in independent CLI runs
and renders 61 notes to a 12.201333 s WAV (peak 0.159019, RMS 0.036000). A captured
anchor/tempo/undo take also renders successfully. A saved timed history submitted
to the real PipeWire speaker route completes all 61 voice lifecycles at 48 kHz /
256 frames; its server and monitor are stopped afterward. No separate listener
assessment of this M0.6 run is claimed. Headless Qt/real-time-priority warnings
remain environmental limitations. No new controls were injected during audio.
