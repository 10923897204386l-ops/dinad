# M0.3: project configuration and semantic controls

M0.3 adds versioned TOML settings and keyboard-driven mock composition sessions.
Install Python 3.11+ and run `python -m pip install -e '.[dev]'`.

## Project and profile files

```sh
python -m dinad validate examples/first_environment/project.toml \
  --profile examples/first_environment/controls.toml
python -m dinad parameters
python -m dinad demo --project examples/first_environment/project.toml
python -m dinad session --project examples/first_environment/project.toml \
  --profile examples/first_environment/controls.toml
```

Both file formats require `schema_version = 1`. Omitted project sections/fields
use defaults. Unknown fields, unsupported versions, wrong types, non-finite
numbers and out-of-range settings fail with the filename and field context.
`demo` flags explicitly supplied on the command line override project values;
unspecified flags preserve the project's settings. Relative CLI file paths are
resolved from the current directory. Profiles are selected explicitly with
`--profile`; no implicit file search or executable configuration is used.

The first project schema configures the built-in M0 composition:

| Stable parameter ID | TOML field | Default | Range | Unit |
| --- | --- | --- | --- | --- |
| `composition.anchor` | `[composition] anchor` | 48 | 0–127 | Semitones, C4=60 |
| `transport.tempo_bpm` | `[transport] tempo_bpm` | 120 | 1–1000 | BPM |
| `generation.seed` | `[generation] seed` | 0 | 0–9223372036854775807 | Integer |

Fractional anchors and tempos are allowed; seeds must be integers (booleans are
not numbers in this schema). The registry is shared by project loading, demo
arguments and session controls. These limits apply to the demo/project settings;
the general object model still supports arbitrary finite semitone relationships.
Parameter metadata includes labels, units, bounds, smoothing and application
semantics. Mock controls have no smoothing and apply on the next generation.

This schema does not yet serialize arbitrary object definitions or instrument
routing. Global `config/defaults.toml` and navigation `config/keymap.toml` remain
bootstrap design examples, not runtime settings. Audio, plugin and routing
sections in project files are rejected rather than silently ignored.

## Commands

The session accepts one line per command, submitted with Enter. A real terminal
shows a prompt; piped input works without a terminal or audio device.

```text
inspect
set composition.anchor 60
adjust transport.tempo_bpm 5
key +
undo
generate
save "renders/session.json"
quit
```

- `inspect` prints the current parameter values as JSON.
- `set ID VALUE` and `adjust ID DELTA` validate an entire candidate configuration
  before committing it. `adjust` is relative to the current value.
- `key TOKEN` resolves a configured profile binding to the same semantic command
  parser. The example `+`/`-` bindings move the anchor a semitone, `f`/`s` change
  tempo, `u` undoes, `g` generates, `i` inspects and `q` quits. Keys are line
  tokens, not raw keypress listeners. Duplicate keys, unknown parameters,
  malformed commands and invalid fixed values are rejected when loading.
- `undo` restores the last successful set/adjust operation. Repeated undo walks
  back earlier changes; there is no redo command. Failed commands consume no
  undo entries. Undo itself is recorded as a semantic change.
- `generate` writes a complete resolved JSON history to stdout without changing
  settings or consuming persistent RNG state. Each generation restarts its seed.
- `save PATH` generates a fresh resolved history for current settings and writes
  it atomically. The parent directory must exist. An existing file at PATH is
  replaced only after the full history has been generated and written.
- `quit` or EOF ends the session. Command errors go to stderr, leave settings
  unchanged, and allow the session to continue; its exit code is 1 if any command
  failed. Invalid startup files/arguments exit with code 2.

Profiles may map inspect, set, adjust, undo, generate and quit. They cannot write
files, invoke other keys recursively, execute shell commands or evaluate Python.
Profile adjustment deltas are checked for numeric validity at load time and for
resulting parameter bounds when invoked. A well-formed profile does not promise
that every relative adjustment is valid at every current value.

## Capture and reproducibility

A saved recording retains the resolved event array using recording schema 1.
Additional metadata includes project schema/version, the final settings snapshot,
the selected profile snapshot, and semantic-action schema 1: initial settings
and ordered changes with sequence, parameter ID, old value and new value.
`set` and `adjust` have the same meaning whether typed or mapped to a key.
Read-only commands and file saves do not add parameter changes.

The saved events are generated from the final snapshot, not by replaying all
historical settings as a timed performance. Existing `python -m dinad replay`
continues to submit stored events directly; it ignores settings, action metadata
and RNG. Old M0.2 recordings remain readable. Use `save` to obtain a recording
file; interactive stdout mixes inspect/action responses with generated JSON.

This is a mock composition session. Settings changes apply to the next generated
schedule. Timed live control capture on an audio-clock transport, active-voice
retuning, MIDI hardware, profile overlays, and full project object serialization
remain pending. No real audio is started by these commands.

## Scripted smoke example

```sh
mkdir -p renders
printf '%s\n' 'key +' 'undo' 'save renders/session.json' 'quit' | \
  python -m dinad session --project examples/first_environment/project.toml \
  --profile examples/first_environment/controls.toml
python -m dinad replay renders/session.json
python -m pytest
```

Generated JSON and logs remain outside Git. The next integration is M0.4's
provisional SuperCollider adapter; audio-clock dispatch and note lifetimes must
be implemented before claiming live playback or live timed control support.
