# M1.1 — module contracts and existing adapters

This increment introduces the headless module boundary, preserving M0 CLI and
recordings. It does not implement module discovery, TOML binding configuration,
continuous transport or external plugin hosting (M1.2–M1.5).

## Contracts

`dinad.events.Event` is the existing immutable resolved note command: instrument,
pitch, onset seconds and positive lifetime. `dinad.engine.Event` remains an alias.
It includes note-off intent through duration; it does not claim MIDI velocity,
channel, pitch bend, sample offsets or audio-clock synchronization.

`dinad.modules` supplies immutable, validated descriptors:

- `ModuleDescriptor`: stable module ID and exact adapter version, typed kind and
  capabilities, dependencies per capability, audio ports, optional versioned state
  compatibility ID and explicit limitations. Contract version is integer 1.
  `headless=False` is rejected. This flag is a provider contract, not a sandbox
  for executing untrusted plugin code; no dynamic plugin execution is added.
- `ParameterDescriptor`: native ID, type, optional known default, numeric bounds,
  units, enum choices, read/write flags, automation rate and optional smoothing /
  update-rate constraints. Unknown values stay unknown (`None`). Defaults are
  validated; booleans are not numbers, integer parameters reject floats, and
  invalid/non-finite values fail before provider interaction. Writable/automation
  declarations must be consistent with module capabilities.
- `SemanticBinding`: schema-1 DINAD semantic ID and one or more `BindingTarget`s.
  Targets pin exact module ID/version/native ID and declare finite linear
  scale/offset intent. `validate_target` checks the declared target, version and
  write access. Renamed/missing IDs and version mismatches fail explicitly.
  No semantic meaning is inferred from a vendor parameter's name. These are
  data contracts only: no registry, config loader, value mapping, normalization,
  smoothing, automation execution or migration engine is implemented here.
  A future consumer must validate mapped values against target descriptions;
  declarations do not authorize silent clamping or type conversion.
- `EventReceiver`, `ModuleAdapter`, `NoteAdapter`, `ParameterReader`/`ParameterWriter`,
  `OfflineRenderer` and `ScheduledPlayer` define structural Python interfaces.
  `engine.Backend` remains the minimal `EventReceiver` alias, so legacy objects
  implementing only `submit(Event)` still work with `replay`. Full M1 adapters
  additionally expose descriptors and `prepare`/`close` lifecycle methods.
  The base `ModuleAdapter` needs no note input; `NoteAdapter` adds that optional
  interface, so production effects are not forced to receive musical notes.

Check `descriptor.require(capability)` before optional operations. Unsupported
capabilities and unknown parameters raise `UnsupportedCapability`; this is never
permission to launch a plugin editor. The optional operation protocols do not
promise that every adapter implements them. Renderer/player keyword options
remain provider-specific M0 compatibility options; a generic transport/host API
is outside this increment.

## Built-in adapters and lifecycle

| Adapter | Declared support | Parameters |
| --- | --- | --- |
| `dinad.mock@mock-v1` | Stage/record resolved notes | None; no audio |
| `dinad.supercollider@supercollider-v1` | Stage notes, offline render, scheduled playback, read settings | Requested sample rate, finite scheduled tail, preroll |

The SuperCollider descriptions refer to DINAD adapter settings, not discovered
plugin controls. Reads return the instance's actual settings, while descriptor
defaults describe constructor defaults. There is no live parameter-write,
preset or DSP-state capability. The master output is the existing fixed stereo
bus; audio-device negotiation and actual latency remain unknown. Tool dependency
declarations do not establish availability or engine version compatibility.

Both constructors remain immediately ready to **stage**, preserving M0 behavior.
`prepare()` is idempotent and opens no process/device; it does not establish engine
readiness. Rendering/playback still perform existing bounded validation and engine
checks. `close()` is idempotent and terminal; history and descriptors remain
inspectable, but new submit/render/play/prepare calls fail. Create a new instance
to reopen. These synchronous staging adapters own no process between operations;
close is not concurrent playback cancellation or panic/note-off for another thread.
Existing live execution retains its failure cleanup and voice-lifecycle checks.

The DINAD CLI now calls `dinad.execution` application functions instead of the
concrete SuperCollider adapter. That layer selects the existing built-in provider,
checks the operation capability, stages resolved events and closes the adapter on
success, staging failure or execution failure. There is no module registry yet.
Direct M0 adapter and low-level render/play imports remain available to callers.

## Compatibility and validation

Recording schema 1, project/profile schemas, event ordering, note gate lifetimes,
mock/SC version strings, CLI options and M0 synthesis assets remain unchanged.
No vendor GUI, UI framework, new runtime dependency or plugin implementation is
introduced. All public user configuration still enters through DINAD's existing
files and controls; module configuration/binding files are M1.2 work.

Run `python -m pytest` headlessly; the optional actual SuperCollider test still
uses the existing `DINAD_TEST_*` settings. Focused tests cover typed descriptions,
access/version failures, headless-only declarations, legacy receivers, staging
without external processes, instance setting reads, closed-adapter behavior and
application-layer cleanup. Existing M0 regressions remain part of the suite.

Local validation (11 November 2026): 219 tests passed in the source checkout
and against a fresh wheel using the source distribution's tests, on Python
3.14.8 with SuperCollider 3.13.0. Pre-refactor demo and timed-performance JSON
match byte for byte; legacy replay still reports 61 events through `mock-v1`.
The installed CLI rendered that existing history to a valid 48 kHz stereo WAV
of 10.201333 s, peak 0.139662 and RMS 0.036196. This is offline evidence; no new
hardware listening, external plugin compatibility or minimum-Python-version
validation is claimed.
