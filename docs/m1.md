# M1 — DINAD-native headless modular instrument architecture

Status: **M1.1 and M1.2 implemented. M1.3 in progress under its original scope; M1.4–M1.6 planned**. See [M1.1 contracts and compatibility](m1-1.md) and [M1.2 module configuration](m1-2.md). This document defines the full M1 implementation contract, not a claim of working external plugin hosting.

## Product rule: DINAD is the only front end
DINAD's fixed, modal keyboard/knob/pad/display interface is the **only** application user interface. All ordinary plugin selection, configuration, parameter editing, presets, mappings, automation, diagnostics and saved state are managed through DINAD's UI and human-readable DINAD configuration files. The plugin's own bespoke GUI must never be opened, embedded, required or treated as a configuration fallback. No plugin UI framework is part of the product.

Plugins are headless synthesis, processing or musical-behaviour providers. They do **not** need to know DINAD's musical object model. DINAD interpreters resolve musical objects to semantic events and controls; an adapter translates those into a plugin's exposed capabilities.

### Compatibility boundary
A plugin is compatible to the extent that it exposes usable programmatic interfaces for note/event input, parameters, state and audio routing. MIDI-only devices may be supported with reduced capabilities. If a feature is accessible only through a vendor GUI, explicitly report it as unavailable; do not secretly launch that GUI. Opaque plugin state may be retained as a supplementary versioned asset for faithful recall, but all user-facing configuration and mappings must be represented by DINAD files. Do not claim that all plugins can be fully configured through a generic API.

## Logical layers
1. **Fixed DINAD front end**: controls, context banks, text configuration editor, diagnostics.
2. **Application model and parameter registry**: stable semantic IDs, units, bounds, smoothing, transactions, validation, state and automation.
3. **Musical object engine**: reusable objects, interpreters, harmonic context, clocks, event generation and replay.
4. **Module registry and capability negotiation**: identify modules, validate versions, discover inputs/outputs/parameters/presets and limitations.
5. **Adapters**: translate semantic events/parameter bindings to MIDI, LV2, SuperCollider or later transports.
6. **Headless execution and audio graph**: host/engine process owns DSP, timestamped delivery, routing, latency, fault isolation and rendering.

The front end must never call a plugin or SuperCollider directly. Avoid placing LV2 hosting inside SuperCollider as a default assumption: investigate a dedicated host with a shared transport/audio graph.

## Native module classes
- Musical: object interpreters, transformations, harmony evaluators.
- Performance: arpeggiators, clocks, generative rules, modulation and scheduling.
- Instrument: MIDI/note-driven synthesis or sampling, including SuperCollider and externally hosted plugins.
- Production: effects, routing, buses, metering and dynamics.

These are **contracts/capabilities**, not mandatory rigid categories for musical objects. Prefer ordinary Python interfaces for musical modules and native audio-host APIs for DSP. Do not dynamically execute arbitrary untrusted Python plugin code without an explicit security design.

## Required capability contract
Each module declares stable identity, version, kind, capabilities, required dependencies, lifecycle and state compatibility. Instrument/effect adapters should expose, where supported:
- timestamped note on/off, velocity, channel, pitch bend and expressive events; transport/tempo when supported;
- parameter enumeration with stable plugin-native identifier, type, min/max/default, units, enum values, automation rate and readable/writeable status;
- typed parameter set/get with validation, unit translation, normalization, smoothing and bounded update rate;
- preset/program selection and state save/restore (including opaque supplementary state when needed);
- audio/MIDI input/output ports, routing, channel count, latency, tail and render capabilities;
- explicit unsupported-capability diagnostics, crash/timeout reporting and clean resource lifecycle.

**No fabricated semantic interpretation of unknown plugin parameters.** DINAD semantic mappings are declarative, inspectable and versioned. Mapping may be one-to-many, with curves/scales and explicit constraints. If parameter IDs or plugin versions change, fail visibly and offer migration rather than silently binding to the wrong parameter.

## Timing and replay
A shared audio-derived clock and ordered timestamped event stream must coordinate all modules. Preserve event ordering and note-offs; account for transport, automation and plugin latency. MIDI clock is not sufficient for sample-accurate events. Live, recorded and offline execution must use the same resolved musical decisions; distinguish reproducible event history from bit-identical plugin audio.

## Configuration policy
Use schema-validated DINAD TOML or other explicitly versioned human-readable DINAD files for project instruments, bindings, controls, presets, routing and automation. Global preferences remain separate from project overrides. A plugin may have an opaque state blob for recall, referenced by DINAD configuration; it must not be the sole user-editable configuration surface. Changes are transactional where feasible and logged as semantic actions. Unknown parameters or incompatible versions produce actionable errors.

## M1 sequence and acceptance
**M1.1 — Contracts and adapter refactor.** Define typed module/capability/parameter descriptors and event interfaces; adapt existing SuperCollider and mock implementations without changing M0 behaviour. Headless tests for compatibility and reproducibility.

**M1.2 — Registry, binding and config.** Discover built-in modules and expose parameters; validate DINAD config and one-to-many semantic mappings; test changing a module without changing front-end control IDs.

**M1.3 — Continuous live performance.** Persistent clock/transport, timed live semantic control changes, start/stop/replacement with safe note release and state handling. Test long-running sessions and failure recovery.

**M1.4 — PySide6/Qt Widgets performance shell and DINAD F12 drop-down configuration editor.** Build a minimal single-window PySide6/Qt Widgets DINAD performance panel (transport/status, selected object and basic semantic controls), plus the functional DINAD-native, keyboard-first drop-down text editor over that panel. F12 toggles it; edit actual schema-validated DINAD project/config files with syntax highlighting, visible file path and dirty state, clear line/column errors, save/reload, and Ctrl+S validate-and-apply. Apply safe changes transactionally during continuous playback without unnecessary interruption; invalid edits leave the running state untouched. Explicitly mark changes that require stop/restart or audio-graph rebuild; never silently apply them. Preserve original file and runtime state on failed validation/application. Use Qt Widgets text editing and syntax highlighting; preserve a headless core and CLI, and keep GUI event handling off the audio scheduler. No third-party plugin GUI, no parallel config format, no requirement for M3 visual polish. See [frozen GUI technology decision](gui-decision.md).

**M1.4 HANDS-ON GATE — mandatory pause before M1.5.** On Fedora, complete a 30–60 minute hands-on session: sustained playback; F12 opening/closing without interruption; live tempo, harmony, density and synthesis control changes; Ctrl+S success/invalid edit rollback; keyboard navigation, feedback, CPU/underruns and log inspection. Record observations, limitations and pass/fail. Fix blocking usability or audio defects in small PRs before starting external plugin hosting. Do not treat automated tests as a substitute for listening.

**M1.5 — External plugin feasibility and first integration.** Investigate existing LV2 hosting and sample-offset event/automation transport, then integrate one verified Linux instrument (ZynAddSubFX/Yoshimi where suitable, or another instrument exposing the necessary interfaces). Do not assume a named synth has a compatible LV2 build; inspect actual packaging and capabilities. No plugin-native GUI. Verify notes, discovered parameters, saved/restored state and offline/live timing on Fedora. Document unsupported features. Conduct a second short hands-on check of plugin sound, parameter mappings and save/restore.

**M1.6 — Playable instrument evaluation.** Keyboard-driven DINAD control surface (initially minimal), drone/pad/arpeggiator, shared harmonic changes, generative evolution, basic routing, recording/replay, diagnostics, sustained listening and CPU/underrun evidence.

Gate: A musician can configure and play a compatible third-party instrument entirely through DINAD, alter its parameters via DINAD objects, and capture/replay the musical performance without opening its native editor.

## Build continuity
Do **not** alter, restart or broaden an in-flight original M1.3 build. Merge and validate its original continuous-performance scope first. The revised numbering applies to new work only. M3 retains final interface/editor visual polish, autocomplete, contextual help and advanced ergonomics.

## Non-goals for M1
Full plugin marketplace, arbitrary VST3 support, universal GUI-only feature access, unrestricted hot-swapping of all DSP graphs, full production mastering, finished graphical panel, advanced harmonic tail analysis, and multi-backend distributed synchronisation.
